# 多 agent 协作与派工规则

版本 1.1 · A0 负责设计与验收；独立开发 owner 负责实现与集成

当前按 [ADR15](../adr/0015-unity-client-and-design-only-a0.md) 和 [U01](../tasks/U01/TASKBOOK.md) 执行。编写派工卡不等于启动开发任务；用户决定在其他会话开始实现。A0 本会话可修改设计/台账、只读检查和验收已有产物，不安装 SDK、不创建或修复产品工程。

## 1 角色与目录归属

角色是职责，不要求同时启动九个 agent。一个 agent 可以先后承担多个角色，同一时刻每个文件只有一个任务 owner。任务级允许修改范围以 planning/tasks.json 为准。

| 角色 | 负责内容 | 主要目录 |
|---|---|---|
| A0 主架构与验收 | 需求、ADR、接口设计、任务依赖、审阅与验收结论 | 设计/协作文档、设计台账、验收报告；不在本会话实施工程修改 |
| A1 后台与数据 | 认证、设备、会话、调度、记忆、迁移 | services/api/app 的核心模块 |
| A2 云端 AI 与语音 | ASR、LLM、TTS、取消、用量、供应商比较 | services/api/app/providers |
| A3 Unity 界面与角色 | Unity 工程集成、角色、聊天与设置；实际子任务单独 owner | apps/unity 的 UI、Avatar、Scenes、Prefabs、工程设置 |
| A4 客户端运行时与桥接 | C# 会话、网络、桌面音频、未来原生接口 | apps/unity 的 Session、Transport、Audio；共享 Contracts 由集成 owner 单写 |
| A5 iOS | 后续原生语音、生命周期、灵动岛、签名与 Unity 桥接 | native/ios 与 Unity iOS 插件目录，须先重新派工 |
| A6 Android | 后续原生语音、前台服务、通知与 Unity 桥接 | native/android 与 Unity Android 插件目录，须先重新派工 |
| A7 直播接入 | 权限验证、平台连接、事件标准化 | services/api/app/live |
| A8 验收与交付 | mock、契约测试、集成、部署、验收报告 | tests、infra、docs/reports |

A0 与模块 owner 共同审阅共享接口变更。A8 检查实际结果，不通过改验收门槛掩盖失败。产品范围、角色审美、资金和对外发布由项目负责人决定。

## 2 建议执行批次

近期先执行 U01 的 U-G0/1/2 批次；该任务书已提供独立的目录与前置条件。下表保留完整 R1 顺序，被标记 changed 的客户端任务必须重写实现卡再领取。G0 真机条件缺失不阻止 U01 本机原型，但不能被原型替代。

| 批次 | 任务 | 结束后的可用成果 |
|---|---|---|
| 0 | T00 | 正式仓库、依赖版本、可读契约 |
| 1 | T01、T02、T03；有空闲能力时 T04 | 手机与平台证据、离线模拟链路 |
| 2 | T05、T06、T09 | 云能力、会话服务、角色渲染 |
| 3 | T07、T08、T10、T11、T14、T16，按依赖分批 | 桌面、手机界面和运行底座 |
| 4 | T12、T13、T15、T17 | 双端原生集成、直播调度、桌面验收 |
| 5 | T18、T19 | 手机和直播真机联调 |
| 6 | T20 | 完整 R1 验收与可安装产物 |

若同时可用的 agent 数量有限，保留一个协调角色，每批启动两到三个边界互不重叠的任务。批次用于阅读，真正能否开始以 tasks.json 的 depends_on 为准。证明技术可行的短实验必须保留可复现说明，后续任务不得把实验代码直接当成已完成产品。

## 3 每次派工必须包含的信息

1. 任务 ID、目标、输入材料和依赖任务的提交版本。
2. 允许修改的目录、禁止修改的共享文件和任务 owner。
3. 要实现的契约、mock 入口、错误与取消行为。
4. 验收编号和必须提交的真实证据。
5. 已知外部条件、应向 A0 汇报的决策，以及交付位置。

agent 在开始前读取 ARCHITECTURE、相关 CONTRACTS、自己任务和对应验收条目。无需依赖当前聊天记录，也不应把其他任务的临时推测当作架构决定。

## 5 A0 的工作方式

A0 持有任务台账，记录任务状态、分支、提交、当前 owner 和依赖。先让契约和 mock 可运行，再放开并行实现。收到接口冲突时比较实际调用需求，统一修订并通知全部消费者，避免让两个 agent 私下形成第二套协议。

A0 在具备运行条件时验收已有跨模块候选包；条件不足时明确哪些证据仅由独立 QA 提供。代码合并、冲突修复与构建由指定开发集成 owner 完成。顺序通常为契约和 mock、服务端、客户端、端到端验证。必须同时生效的协议变更由 A0 设计过渡方案，开发 owner 实施，不让主分支持续处于无法运行的中间状态。

A0 保留以下决策权：模块分界、状态机、共享标识与事件、传输格式、存储边界、技术选型变更和版本发布判断。遇到用户目标、预算或公开发布变化时，向项目负责人说明具体选项和影响。

## 6 分支与共享文件

每个任务使用 task/Txx-short-name 分支。多台机器或多个 agent 需要并行时使用独立 worktree；共享真实数据库前先统一迁移流程。完成一个逻辑单元后提交，切换机器前推送，接续机器先同步。

根依赖锁、CI、schema、数据库迁移顺序、Unity ProjectSettings/Packages/总场景以及原生构建文件属于协调文件。A0 审阅变更设计，在台账登记负责写入的开发 owner；不要由多个 agent 同时重写，A0 本会话不代改实现。跨平台桥接由 A4 提案，A0 审阅，开发集成 owner 统一落地。

正式 GitHub 仓库建立后，优先通过小 PR 集成。PR 包含解决的问题、最终行为、相关任务与验收编号、验证结果和限制。PR 名称与描述围绕最终实现，不保留无关的试错记录。

## 7 任务状态

- ready：依赖已满足，可以领取。
- in_progress：有明确 owner、分支和开始版本。
- awaiting_external：真实设备、平台权限或密钥缺失；其他工作继续推进。
- review：实现、测试与交接报告齐全，等待检查。
- done：验收证据满足，已集成并更新台账。
- changed：经 A0 或项目负责人批准改变范围，并有决策记录。

初始任务清单均为 planned，依赖图只是设计计划。不要在没有代码和证据时预先标记 done。某个测试失败时报告失败原因与影响，不把任务改写成只需要通过 mock。

## 9 独立审阅要求

关键跨端任务由未编写该模块的 agent 检查：A5 的音频由 A8 在 iPhone 上验收，A6 在 Android 上验收，A1 的取消和隔离由 A8 构造竞争条件，A7 的真实弹幕由 A0 或 A8 核对来源。独立审阅需要真实执行证据；仅阅读实现并表示同意不等于通过。

本交付包本身已经进行文档、依赖和契约一致性检查。将来工程阶段仍需上述独立运行审阅，不能把文档检查当成应用验收。
